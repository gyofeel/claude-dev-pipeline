# TC file format

Shared standard consumed by three skills: `e2e-test` (batch mode parser), `tdd-implement` (unit targets), and the orchestrators (gate metrics). `####` sub-section names and the **bold** metadata field names are parse keys — keep them exact. Do not add values to enumerations (`E2E suitability`, checkpoint `Type`); add rows instead, which parsers ignore safely.

## File header

```markdown
# <Feature name> Test Cases

> **Created**: YYYY-MM-DD
> **Scope**: <screen > component>
> **Related files**: <comma-separated paths analysed> (new-implementation mode: prefix planned files with `(new)`)
> **PRD**: <prd path>
> **TC count**: N          (new-implementation mode: `N (unit N · e2e N · manual N)`)
> **Implementation mode**: new    ← present ONLY in new-implementation mode
> **Generated by**: /dev-pipeline:tc-extract
```

Then `## Overview` (2–4 sentences), `## Acceptance Criteria` (copied `- [ ] **AC-NN**:` list), `## Test Cases`.

## One TC = `### TC-NN: <name>` + 8 fixed sub-sections + 1 optional

Each TC ends with a `---` line.

### `#### Metadata` — 12-row, 2-column table

| Field | Allowed values | Consumer |
|---|---|---|
| **TC ID** | `TC-01` | — |
| **Spec file** | `<specFilePrefix>tc01-<kebab>.spec.js`, or `(none)` for unit-only TCs | e2e-test batch: output file name |
| **Priority** | `High` / `Medium` / `Low` | — |
| **Type** | `happy path` / `error handling` / `ui` / `boundary` / `regression` | — |
| **Related AC** | `AC-01, AC-02` | traceability |
| **E2E suitability** | `e2e` / `manual` | `manual` TCs are listed under `## Manual review items` and skipped by e2e-test |
| **Screen** | free text (the page/feature area) | `analyze()` `domain`; screen-context lookup |
| **Start URL** | path or `/` | `START_URL` |
| **Fixtures** | comma-separated file names in `e2e.fixturesDir`, or `(none — live API)` | `mockAll` route map |
| **AI verdict** | `PASS only` / `WARNING allowed` | `ACCEPTABLE_STATUSES` |
| **Console error whitelist** | `(none)` or comma-separated substrings | `CONSOLE_ERROR_WHITELIST` |
| **Unit target** | `(none)` or repo-relative test file path | tdd-implement: becomes the plan task's `Test:` line |

`Unit target` is orthogonal to `E2E suitability`: all four combinations are valid and **a TC is never split** to separate them. It holds a path, not a boolean, so the plan generator never invents file names.

### `#### Preconditions`

Bullets. API mocks as `**API mock**: <url pattern> → <fixture file>` (one per line). Patterns are Playwright globs and must end with `*` when the request carries a query string (`**/api/gnb/list*`) — copy the shape existing specs use. Include the boot-critical fixtures `fixture-advisor` lists even when the TC does not exercise them; an isolated run cannot boot without them. Also login state, data prerequisites. If nothing: `- none`.

### `#### Entry path`

Numbered steps in the entry-path DSL (below). Each step: inline code, then ` — ` and a short purpose.

### `#### Render-ready condition`

Three fixed bullets:

- **Method**: `waitFor expr` / `waitFor selector` / `app ready only`
- **Expression**: `<js boolean>` or `<css>` — `N/A` when app ready only
- **Timeout**: `<ms>` — `N/A` when app ready only

### `#### Checkpoints`

5-column table, ids `CP-01`, `CP-02`, … Each row becomes one `SUCCESS_CRITERIA` entry and one `test.step` assertion.

| CP ID | Type | Target / Path | Condition | Description |
|-------|------|---------------|-----------|-------------|

- `Type` ∈ `DOM` / `Focus` / `State` / `Runtime` — no other values
- `Target / Path` by type:
  - `DOM` → target descriptor: bare CSS (`.list-item`), or `testid:<value>`, `role:<role>[name]`, `text:<text>`
  - `Focus` → `activeElement` (pointer projects) or the app focus expression name when `adapter.focusExpr` exists
  - `State` → `<store>.<field.path>` relative to `ui.stateBridge.globalExpr` (only when the bridge is configured)
  - `Runtime` → `consoleErrors` / `networkErrors`
- `Condition` by type:
  - DOM: `visible` / `hidden` / `hasText('…')` / `hasClass('…')` / `not hasClass('…')` / `count(N)`
  - Focus: `matches('<css>')` / `hasText('…')` / `includes('…')`
  - State: `truthy` / `falsy` / `toBe('…')` / `toEqual(…)` / `matches /re/` / `length(N)`
  - Runtime: `isEmpty` / `filteredCount < N`

Values come from code that was actually read. Unverifiable entries are written as `[verify: selector not found]` / `[verify: state path not found]` and raised at the review step. In new-implementation mode, predicted values carry a `(new)` suffix.

### `#### Success criteria`

`> ` blockquote, 1–3 sentences in user language, covering all checkpoints. Passed verbatim to `analyze()` as `successCriteria`.

### `#### Expected results`

Numbered list, each `<result> — CP-NN`.

### `#### Notes` *(optional; omit when empty)*

Known behaviours, soft-pass conditions, environment dependencies. New-implementation mode must include:

`> Predicted selectors for new implementation — verify after implementing`

### `#### Unit checkpoints` *(only when Unit target ≠ (none))*

| UCP ID | Target (module#export) | Input / state | Expect | Description |
|--------|------------------------|---------------|--------|-------------|
| `UCP-01` | `~/lib/filter#byGenre` | `items: […], genre: 'x'` | `toHaveLength(2)` | returns matching items |

- `Target` = exact import specifier + `#` + export name → becomes the plan's `Interfaces: Produces`
- `Expect` = a literal matcher expression (`toBe`, `toEqual`, `toHaveLength`, `toThrow`, `resolves.toEqual` …)
- expected values are **hand-computed literals**, never derived by re-running the code under test
- unit test names follow `it('UCP-NN: <description>')` — the exact `--test` target of `red-gate.mjs`

## Entry-path DSL

| Step | Meaning |
|---|---|
| `goto('<url>')` | navigate, wait `domcontentloaded` |
| `waitForAppReady()` | `adapter.waitForAppReady` with the TC's render condition |
| `click(<target>)` | `adapter.locator(target).click()` |
| `fill(<target>, '<text>')` | type into an input |
| `press('<KEY>')` | one logical key via `adapter.press` |
| `waitFor: <expr or css> / { timeout: <ms> }` | wait for a condition |
| `loop press('<KEY>') × max N: <expr> → break` | state-based loop; **fixed repeat counts are not allowed** |
| `findAndEnter(<target>)` | goal-directed activation via the adapter |

`<target>` uses the same descriptor forms as checkpoints. Keys are logical names (`Enter`, `ArrowDown`, `Escape`, …) mapped by the adapter.

## File-level trailing sections

### `## Manual review items` *(when any TC is `manual`)*

| TC ID | Name | Exclusion reason | Manual checkpoint |
|-------|------|------------------|-------------------|

If a manual TC has a `Unit target`, add `unit-verified` to the reason so reviewers do not duplicate what the runner covers.

### `## Implementation surface` *(new-implementation mode only)*

| Planned path | Kind | Nearest sibling | Sibling test | Registration | Mocks needed | TCs |
|--------------|------|-----------------|--------------|--------------|--------------|-----|

Every path here was confirmed on disk (siblings) or is explicitly `(new)`. `tdd-implement` fills plan `Files:` and `Interfaces:` from this table. Batch parsers ignore this section.

## Priority and type rules

| Priority | Rule |
|---|---|
| High | core flow, directly maps an AC, failure blocks the feature |
| Medium | secondary behaviour, error handling, UX polish |
| Low | regression, boundary, cosmetic |

| Type | Meaning |
|---|---|
| happy path | intended behaviour |
| error handling | API errors, empty data, network failure |
| ui | visibility, focus, layout |
| boundary | min/max, 0/1 items, timeouts |
| regression | adjacent existing behaviour still works |
